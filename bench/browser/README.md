# Browser benchmark: the `state()` prototype against plain JavaScript, Solid and Remix 3

A test of one proposal for Corten's browser side. A component's script is a setup function with
plain variables and one `state({...})` object. Assigning a new value to a state key re-runs, in
a microtask, only the renders that read that key: there is no `update()` call, no virtual DOM
and no signal per value. Lists are `<template>` clones that a keyed `list()` patches. The
prototype runtime is [apps/shared/state.js](apps/shared/state.js), 2,147 B gzip
on its own as first measured (2,291 B after the fixes below). Nothing in the framework uses it yet.

Every app renders the same rows (the js-framework-benchmark word lists, the same 32-bit LCG and
the same markup), and the harness measures all of them from outside with the same code.

| App | What it is | Code |
|---|---|---|
| vanilla | Plain JavaScript written for speed, the floor | [apps/vanilla](apps/vanilla/app.js) |
| state | The proposal: `state`, `list`, `mount`, and a row template whose fill function the Rust macro would generate | [apps/state](apps/state/app.js) |
| view | Plain JavaScript as the framework: handlers write a view's named holes (`row.label = x`); no state, tracking or scheduler. `Row` is generated by `#[component(view)]` from the Rust component in [gen/src/main.rs](gen/src/main.rs), which also renders the page with `html!` | [apps/view](apps/view/app.js) |
| solid | Solid 1.9.17 with its compiler, written like the js-framework-benchmark's keyed Solid app (a signal per label, `createSelector`) | [apps/solid](apps/solid/rows.jsx) |
| solid-h | Solid without a compiler, through the `h`, `each` and `mount` helpers in [apps/solid-h/solid.js](apps/solid-h/solid.js) (Corten served them as `corten/solid` until views replaced them) | [apps/solid-h](apps/solid-h/app.js) |
| remix | Remix 3.0.0 `remix/component`: plain variables and `handle.update()` (the same component as the rmx bench's) | [apps/remix](apps/remix/RowsBench.tsx) |
| react | React 19.3 with `react-dom`, written like the js-framework-benchmark's keyed react-hooks app (one reducer, immutable rows, a memoized `Row`) | [apps/react](apps/react/rows.jsx) |
| svelte | Svelte 5.57 with runes, written like the js-framework-benchmark's keyed Svelte app (a `$state` label per row, the rows in `$state.raw`) | [apps/svelte](apps/svelte/App.svelte) |
| vue | Vue 3.5 single-file component, written like the js-framework-benchmark's keyed Vue app (a `shallowRef` of rows, `triggerRef`, `v-memo`) | [apps/vue](apps/vue/App.vue) |

Each app is one esbuild bundle, minified, built for production (`NODE_ENV=production` and the
`production` export condition, as Vite does). Solid's JSX goes through `babel-preset-solid`,
Svelte through `svelte/compiler` and Vue through `vue/compiler-sfc` with the template inlined;
the server-rendered pages come from each framework's own server renderer (`renderToString`,
`svelte/server`, `vue/server-renderer`) and hydrate with its own client.

## Running it

```sh
cd bench/browser
npm install
node build.mjs          # out/<app>/: index.html and app.js, and sizes (runs gen/ with cargo for the view apps)
node list-check.mjs     # list() against 3,000 random edits in a real DOM
node view-check.mjs     # rows() (corten/views) against 3,000 random edits, some made without it
node run.mjs            # client operations, memory and load (two rounds, in alternating order)
node ssr.mjs            # 1,000 server-rendered rows: take over, then interact
node dashboard.mjs      # 200 cards on one shared store
node state-check.mjs    # state() and render scheduling: batching, key switches, abort
node ab.mjs <prep|-> <click> <app> <app> ...   # interleaved means, for sub-millisecond gaps
node run-all.mjs <round>     # build, run, ssr and dashboard into results/<round>/, then the table
node summarize.mjs <round>   # the README table from results/<round>/
```

On a Linux droplet: `node bench/fullstack/droplet.mjs <round> --ssh-key <id> --suite browser`
runs the fourteen-framework browser pass of `bench/fullstack` and then `run-all.mjs`.

Takeover on the server-rendered pages is the time from the parser finishing to the app being
ready, less the rendering of any frame the browser paints in between: Chromium paints the
server's rows before the module scripts run on some loads and after them on others (about
100 ms on this page), whichever framework it is. `paintedFirstMs` in the results is that
rendering. Rows the app removes or adds while starting are counted in a separate load, since a
mutation observer slows every app that touches many nodes.

The browser's clock resolves to 0.1 ms here, so differences under a millisecond come from
[ab.mjs](ab.mjs): the apps take turns in blocks of 25 clicks in one browser, and it reports each
app's mean with its standard error.

The harness uses the repository's Playwright and its Chromium.

### Creating many rows

Creating 10,000 rows was profiled against Solid and plain JavaScript on a c-8 droplet (Xeon
Platinum 8280), clearing and creating 60 times per build and alternating builds. Views cost about
27 ms more than Solid; three parts of that were not the DOM work every app does:

| | Cost per 10,000 rows | Now |
|---|---|---|
| The runtime read every `data-ref` of the new rows to learn which ref names joined | about 8 ms | one selector query per name when many rows join one parent |
| `rows().replace` looked up every key in an empty map on a first fill | about 2 ms | skipped when there is nothing to keep |
| `fill` called `toggleAttribute(name, false)` on every new row | about 2 ms | checks `hasAttribute` first |

| Create 10,000 rows (ms, median of 60) | Before | After | Solid | Plain JS |
|---|---|---|---|---|
| Laid out | 89.9 | 78.6 | 63.6 | 61.1 |
| Table hidden (no layout) | 75.8 | 66.5 | 63.7 | 54.2 |

Takeover was the same before and after (5.45 ms each, eight alternating runs of 30 loads), and a
row's heap went from 116 to 101 bytes. With the table hidden, views are within 3 ms of Solid.
What is left is the cost of keeping each row's key and refs in the page: writing `data-key` is
about 4 ms per 10,000 rows and the remaining ref scan 1-2 ms. Moving them out of the page would
give back the takeover and memory that come from reading the page instead of rebuilding it, so
they stay. Building the rows from one HTML string was about twice as slow.

## What these numbers do and do not show

1. Implicit tracking with shallow state costs nothing visible against compiled Solid. Every
   operation's commit is within about half a millisecond of Solid's, and most of them are within
   0.3 ms of plain JavaScript.
2. Shallow state has a measurable price on very large lists. Changing one row of 10,000 copies
   the array and compares 10,000 items, which took 0.5 ms here against Solid's 0.1 to 0.2 ms.
   That cost grows linearly. [Closing the gaps](#closing-the-gaps) brought it to within 0.03 ms
   of Solid.
3. Memory is where signals cost the most. A Solid row holds its signals, owner and computations,
   which came to 927 B. A state row is its item and its element, at 243 B, which is about 77 B
   more than plain JavaScript.
4. Taking over server HTML is the largest gap. The state version has no first render, so it reads
   its refs, runs each render once (which finds nothing to change) and listens for events. Solid
   walks hydration keys and builds its graph. Remix re-renders the tree against the DOM, which
   took 187 ms for 1,000 rows, and then pays 16 to 26 ms on each later interaction.
5. Remix's numbers come from its model rather than from a slow implementation. `update()`
   re-renders the component and diffs every row, so its cost tracks the list's size and not the
   change's size. Splitting the work into components with their own updates (the dashboard) helps,
   but each card still re-renders as a whole.
6. Taking over server HTML was first measured at 12.4 ms for state, because `mount` searched all
   2,000 `data-on` attributes to learn the event types. The server knows those types when it
   compiles, so the prototype now reads them from the root's `data-events` attribute, and the
   time fell to 4.6 ms.

## Closing the gaps

The first run found three places where the proposal lost. All three were fixed or explained
without giving back memory or takeover time: bytes per row went from 243 to 241, and takeover
stayed at 4.2 to 4.5 ms. Every figure below was measured with [ab.mjs](ab.mjs) (mean ms ±
standard error) unless marked.

1. **A change to one row of a long list cost the list's length.** `list.set()` called `key()` on
   every item and built a new element array on every change. It now skips an item that is the
   same object as before, and keeps the element array when no item moved. `node(key)` remembers
   the element it found last, so the selected row is not searched for on every render.

   | commit ms | vanilla | state, first run | state now | solid |
   |---|---|---|---|---|
   | patch 1 of 10k | 0.156 ± 0.014 | 0.380 ± 0.018 | 0.279 ± 0.008 | 0.254 ± 0.012 |
   | patch 100 of 10k | 0.776 ± 0.044 | 1.152 ± 0.049 | 0.989 ± 0.055 | 1.521 ± 0.101 |

   The rest of the gap to Solid on one row (about 0.03 ms) is copying the 10,000-item array, which
   is the price of shallow state. Solid pays more at 100 rows because each changed label is its
   own signal update.
2. **The dashboard tick ran behind Solid.** Profiling showed that most of the state version's time
   was the total's `for (const symbol in prices)`. A `for..in` over a `Proxy` takes the
   engine's slow path: an `ownKeys` trap, then a descriptor and a `get` for every key. Reading a
   known list of keys instead (`for (const symbol of SYMBOLS)`) is the fix. Separately, renders
   now keep their keys between runs and only drop the ones they stopped reading, which saves a
   delete and an add per key on every run. [state-check.mjs](state-check.mjs) covers this,
   including a render that switches keys.

   | commit ms | vanilla | state | state with `for..in` | solid | remix |
   |---|---|---|---|---|---|
   | tick 20 | 0.189 ± 0.003 | 0.369 ± 0.011 | 0.578 ± 0.012 | 0.481 ± 0.008 | 3.937 ± 0.043 |
   | tick 200 | 0.860 ± 0.025 | 1.430 ± 0.026 | 1.673 ± 0.031 | 1.800 ± 0.062 | 33.45 ± 0.68 |

   The rule this implies is that a state object holds named fields. A render that needs
   every key should iterate a list it already has, and `html!`'s generated types can give it
   that list. Development mode could warn when a render iterates a state.
3. **Taking over server HTML depended on `data-events`.** This is not a speed problem: with the
   attribute, takeover is 4.2 to 4.5 ms (median of 15 loads), against 2.3 ms for plain
   JavaScript and 22.6 ms for Solid. The open question was whether the server can write the
   attribute. It can: `html!` already finds every `on:event` in a component and already puts
   `data-scope` on the component's one root, so the union of the event types is known when the
   component compiles. That macro change is part of the port and has not been written yet.
   Reading the server's rows lazily was also tried and dropped: takeover did not change (4.2 ms),
   and the first click got slower (2.2 ms against 1.1).

Everything else stayed the same when [run.mjs](run.mjs) was rerun after the fixes (one round,
[results/ops-fixes.json](results/ops-fixes.json)). [list-check.mjs](list-check.mjs) now also
starts lists from server-rendered elements and checks `item()` and `node()` after every edit.
It passed 3,000 random edits.

Known limits of this test:

1. The row template's fill function and `data-events` are hand-written here. In the proposal,
   `html!` generates both, so the generated code is not yet proven.
2. Development mode (frozen state, and a warning when a render writes state) was off for every
   measurement.
3. Every number comes from one machine and one browser. Firefox and Safari were not run.
4. The Remix figures are for an esbuild bundle, which is smaller than what Remix's own asset
   server sends (42.5 KB gzip in 41 files in the rmx bench).

## Plain JavaScript as the framework: generated views

Where the time goes. Timed one at a time on a warm page (with `out/attrib.mjs`, which is not committed), the
DOM writes cost the same in every app; the extra work is the bookkeeping that finds out what to
write:

| Step | µs |
|---|---|
| one text node write | 0.4 |
| set + get on a plain object / on a `Proxy` | ~0 / 0.3 |
| 200 reads, plain / through a `Proxy` | 0.7 / 11.5 |
| 200 `Map.set` (recording what a render read) | 10.0 |
| `queueMicrotask` and running it | 1.6 |
| copying a 10,000-item array / scanning it by identity | 4.6 / 26.8 |

Plain JavaScript is fast because the handler already knows what changed, so the work is
proportional to the change. `state()` (and Solid, and Remix) let the handler say less, then spend
time finding the change again: through tracking, a scheduled render, and a list compare that is
proportional to the list.

Views keep the plain JavaScript shape and add names and types. For each component used from a
script, `#[component(view)]` generates a class whose properties are its holes, read from and
written to the DOM. [crates/corten/js/view.js](../../crates/corten/js/view.js) adds one function:
`rows(parent, View)`, an array of those views (`at`, `of(event.target)`, `push`, `remove`,
`swap`, `clear`, keyed `replace`). This first round measured the views with a hand-written
class and `state.js`'s `mount` and event delegation; the sections after it run them on
Corten's runtime.

```js
update: () => {
  for (let i = 0; i < list.length; i += 10) list.at(i).label += " !!!";
},
select: (event) => {
  if (selected) selected.selected = false;
  selected = list.of(event.target);
  if (selected) selected.selected = true;
},
```

Interleaved means ([ab.mjs](ab.mjs), commit ms):

| | vanilla | state | view | solid |
|---|---|---|---|---|
| patch 1 of 10k | 0.151 ± 0.009 | 0.272 ± 0.006 | 0.157 ± 0.013 | 0.260 ± 0.010 |
| patch 100 of 10k | 1.032 ± 0.056 | 1.354 ± 0.083 | 0.649 ± 0.011 | 1.804 ± 0.091 |
| update every 10th of 1k | 0.955 ± 0.072 | 1.004 ± 0.059 | 0.691 ± 0.026 | 1.228 ± 0.056 |
| swap | 0.121 ± 0.004 | 0.425 ± 0.014 | 0.124 ± 0.004 | 0.736 ± 0.039 |

The view beats this vanilla app on the two relabel rows. The vanilla app keeps every label twice,
in its `data` array and in the DOM, and writes both; the view keeps it once, in the DOM. That
difference was not profiled further.

From [run.mjs](run.mjs) ([results/ops-view.json](results/ops-view.json)), [ssr.mjs](ssr.mjs)
([results/ssr-view.json](results/ssr-view.json)) and [dashboard.mjs](dashboard.mjs)
([results/dashboard-view.json](results/dashboard-view.json)), medians:

| | vanilla | state | view | solid |
|---|---|---|---|---|
| create 1k (ms) | 7–9.2 | 11–11.1 | 10.7–10.8 | 12.3–12.4 |
| bytes per row | 165 | 243 | 114 | 927 |
| heap with 10k rows (KB) | 2,682 | 3,457 | 2,186 | 10,157 |
| JS (B gzip) | 1,086 | 3,076 | 2,013 | 7,013 |
| takeover of 1,000 server rows (ms) | 2.2 | 3.7 | 2.3 | 16 |
| dashboard tick 20 / 200 (ms) | 0.2 / 0.9 | 0.6 / 1.45 | 0.3 / 0.95 | 0.5 / 1.8 |

[view-check.mjs](view-check.mjs) runs 3,000 random edits (keyed replace, push, remove, swap,
writes through `at`, clear), including lists that start from server-rendered rows, and checks
content, order, kept elements, `at`, `of` and iteration after each one. Its first run found a
bug: `swap` was wrong when the second row came first or the two were neighbors (147 failures);
after the fix it passes with 0.

What this does not give for free:

1. **Derived values.** Nothing recomputes the dashboard's total; the handler that changes a price
   writes it. The pattern that keeps this safe is that one component owns the related DOM and
   exposes methods (`Card.move`, the total in the same handler), so there is one place to forget,
   not one per caller.
2. **State shared between components.** Without a store, a change crosses components as a DOM
   `CustomEvent` or through an `EventTarget`, and each listener writes its own view.
3. **Data that is not on the page.** The view reads back from the DOM, so what is shown is the only
   copy. Values that are not shown (the dashboard's unrounded prices) stay in plain variables.

Known limits (at that commit): the `Row` and `Card` classes were hand-written stand-ins; `replace`
reorders with a simple pass, not a longest-run step; one machine, Chromium only. The next section
replaces the hand-written `Row` with the generated one.

## Generated views, end to end

The view apps run on Corten's own runtime, the way an app serves them. There is no app bundle and
no second handler model: [gen/src/main.rs](gen/src/main.rs) is a small Rust program on the
framework, and its handlers are the components' scripts.

1. `#[component(view)] Row(id: u32, label: &str, selected: bool, select: Ref<..>, remove: Ref<..>)`
   is the row, in `html!`. The macro finds its holes when the crate compiles and generates the
   `Row` class (a getter and setter per hole, `fill`, `key`, `keyOf`) and its declaration. The
   two refs are not holes: they put `data-ref` on the row's links for the bench's handlers.
2. `#[component(js)] Bench` renders `<main>`: buttons with `on:click={js::create(body, template,
   1000)}` and so on, a `<tbody>` with `on:click={js::select(select.closest(), body)}` and
   `on:click={js::remove(remove.closest(), body)}` (one handler for every row), and a
   `<template ref={template}>` with one empty `Row`. [gen/src/bench.js](gen/src/bench.js) is
   its script: plain functions that call `rows(body, Row, template)` and write `row.label`.
3. The dashboard is the same: `#[component(view)] Card` and `#[component(js)] Dashboard`, with
   [gen/src/dashboard.js](gen/src/dashboard.js). Nothing in it is hand-written any more.
4. [build.mjs](build.mjs) writes each page as Corten serves one: the import map (`corten`,
   `corten/views`), the runtime (`crates/corten/js/dist/corten.js`), `views.js` from
   `corten::script::views_module` (`rows()` and the generated classes in one module), and the
   handler module as a module script of the page, ending with the line Corten appends to every
   handler module it serves (a `corten:module` event, written by gen/), with `views.js` preloaded. The JS
   sizes below are those three files.

`npx tsc -p bench/browser/jsconfig.json` checks both scripts against the generated declarations,
and [apps/view/types-check.js](apps/view/types-check.js) holds what it must reject (a misspelled
property, a number written to `label`, a new row without `selected`, a ref passed as data, a
`Card`'s data given to a `Row` list, `rows(body, Card)` on a body of rows, `rows()` of a plain
element, and `push` on rows the server makes). The macro checks the JSDoc:
`js::select(select.closest(), body)` compiles only because `select` is on an `<a>` and `body`
is a `<tbody>` the markup fills with `Row`s only (`@param {Holds<Row, HTMLTableSectionElement>}
body`).

Server-rendered takeover (15 fresh loads, medians; [results/ssr-2026-10-23.json](results/ssr-2026-10-23.json)):
from the parser finishing to the handlers being ready, vanilla 2.1 ms, view 7.2 ms, Solid 25.7
ms. In the same session the previous commit's page (`modulepreload` and the runtime's
`import()`) took 66.9 ms against 7.7 ms for this one.

1. **Updates cost what they did with the bench's first hand-written handlers**, through the real runtime's
   delegation and typed refs: a click resolves `^select` and `@body` and calls the handler, and
   the handler writes one text node.
2. **Creating rows is within the noise of plain JavaScript and Solid.** The runtime wires markup
   that joins the page (it imports the modules it names and records the names of the refs it
   carries) with one query for handlers and one for refs per insert, and reads a run of
   identical ref names once.
3. **The runtime's ref cache survives lists.** A cached ref stays until an element with that ref
   name joins the page or one it found leaves, so the first click after creating 10,000 rows
   costs 0.8 ms, not a query of every row (8.8 ms).
4. **Takeover is no longer the runtime's module loading.** The handler module used to be
   preloaded and then imported with `import()`, which resolved around the first frame (about
   130 to 200 ms after parsing on this 1,000-row page). Now the page loads it as a module script,
   and the lines Corten appends to it hand its exports to the runtime as it runs, before
   `DOMContentLoaded`: 66.9 ms became 7.7 ms, against 2.1 for plain JavaScript and 25.7 for Solid.
   The rest is the module graph (runtime, views, handlers) evaluating and `on:connect` running.
   The seller desk's smoke test clicks a row at `DOMContentLoaded` and checks its handler ran.
5. **Memory is lowest of all** (116 bytes per row): the page holds the rows and the list keeps one
   array of elements.
6. **Which view a parent holds is checked at both ends.** `@param {Holds<Row,
   HTMLTableSectionElement>} body` makes `tsc` reject `rows(body, Card)` and `rows()` of a plain
   element, and the macro reject a ref whose element the markup does not fill with `Row`s only.
